# Scoring and execution details

The parent is a local batch graph (`build.parent()`). It owns ICP compilation, optional explicit
review memory, discovery, independent research/audit, Radar scoring and dispatch. The per-person
child graph (`build.child()`) owns email finding, email verification and the full Alpha Copy graph.
`scripts/run.py` runs the parent, then the child once per dispatched person, then reconciles one
ledger. Neither graph sends messages or enrolls records.

Radar retains the original four dimensions: fit, proof, insight, usefulness. Rubrics and
weights depend on the audience and actual offer. Weighted geometric scoring uses verified
source evidence, freshness decay, contradiction penalties and source-removal sensitivity.
Qualification requires its own score floors, identity check, at least two verified sources,
substantive primary evidence and no disqualifier. These are heuristics.

For each review category, explicit binary feedback updates a Beta(1,1) prior. The ranking
bonus is 8 × (posterior mean − 0.5), bounded within ±4 points. No human feedback means
zero bonus. It cannot change the evidence score or qualification verdict. Feedback IDs
are deduplicated; replacing a person's rating removes the old contribution first.
Memory is scoped to the exact normalized audience/offer brief and Radar settings. Supply
it explicitly (`--memory` with the prior batch's memory.json); it does not fetch past runs by itself.

Copy retains independent evidence, commercial relevance, offer fit, timing and specificity
strengths, weighted 30/25/20/15/10. Every strength must be at least 2/4 and the geometric
score at least 65 by default. Factual checks apply independently. A separate critique and
one revision precede final assembly of greeting, observation, tentative implication, actual
offer, exact CTA and signature. Source and provider names are retained in evidence receipts,
not injected into the email text.

The Finder output is not enough. Finding uses Deepline `findymail_find_from_name` (name + domain;
output `contact.email`), and the address must be on the exact verified employer domain.
Verification uses Deepline `zerobounce_validate` and requires a successful call, an exact returned
address match, status=valid, no adverse sub_status, and free_email false. Missing values
fail closed. ZeroBounce reports catch-all as status=catch-all, which is held. No address pattern
is generated by a model. Each call is 0.28 Deepline credits per result (`deepline tools describe`, 2026-09).

Each source task returns at most ten candidates; the number of tasks is ceil(max_people/10).
Python keeps at most the requested 1–100 distinct people, one per employer. It does not
backfill rejected or unverifiable candidates. Only Radar-qualified people consume email
provider calls and only verified people reach Copy. A fully eligible 100-person batch
can be expensive and slow; start with a small authorized test.

Every dispatched person ends in exactly one terminal child result (EMAIL_HELD, RESEARCH_REQUIRED,
COPY_REVIEW_REQUIRED or DRAFT_READY_FOR_REVIEW). A child that raises becomes PIPELINE_ERROR in
the ledger and the batch continues; inspect that person's run record before any retry so
completed provider work is not bought twice. People run sequentially, so one batch has no
concurrent writes. A batch label is not an idempotency lock: rerunning a batch re-buys every call.
